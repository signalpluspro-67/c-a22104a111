Papier de la semaine · samedi 24 octobre

Agents LLM gouvernés pour investir seuls

Un système de neuf agents LLM qui trade tout seul, avec un noyau de règles qu'aucun agent ne peut toucher.

Governed Self-Evolution for Autonomous Investing: A Multi-Agent LLM System with an Invariant Core · arXiv 2610.30557

PASSER

Mon système est quantitatif et déterministe, les décisions viennent des screeners validés en 8 étapes, pas d'agents LLM qui tradent. Les LLM chez moi écrivent de la prose et classent des setups, ils ne passent pas d'ordres, donc le noyau invariant et le replay trimestriel protègent une surface que je n'ai pas.

Le problème qu'ils attaquent

Quand un LLM trade en live, chaque ordre est irréversible et basé sur du contenu Web qu'on ne peut pas vérifier. Un seul modèle qui lit tout et décide tout dérive vite, oublie ses erreurs passées, et peut se faire injecter des instructions par le texte qu'il lit. Les équipes veulent qu'il apprenne de ses trades, mais apprendre veut dire modifier ses prompts, et modifier ses prompts casse les garde-fous. Il faut donc un cadre où l'agent progresse sans jamais pouvoir réécrire ses règles de risque.

Comment ça marche

👥
01

Neuf agents aux rôles fixés

Quatre analystes lisent des sources séparées. Un pour les news, un pour les filings SEC, un pour la macro, un pour les prix. Chacun rend un rapport dans un format imposé par le code. Un Portfolio Manager lit ces quatre rapports et propose des positions cibles. Un Risk Manager relit la proposition et peut la bloquer. La séparation force chaque agent à défendre sa pièce avec des preuves typées.

🧠
02

Mémoire partagée en sept couches

Avant chaque décision, le code assemble le contexte à donner aux agents depuis l'historique du système. Il y met la position actuelle, le récit de marché en cours, la calibration des agents, les décisions passées de l'agent qui va parler. L'agent ne choisit pas ce qu'il voit. C'est le code qui tape la mémoire et la lui sert déjà filtrée.

📝
03

Note chaque trade la nuit

Chaque nuit, un morceau de code regarde les trades et les prévisions de la journée et leur colle une note chiffrée. La note est écrite dans la mémoire que les agents reliront le lendemain. L'agent voit donc ses propres erreurs la fois suivante. Le scoring est fait par du code déterministe, pas par un autre LLM.

🔁
04

Un trimestre, une mise à jour

Chaque trimestre, un agent réflecteur relit les notes et propose des changements à ajouter aux prompts. Les propositions passent par un filtre déterministe qui refuse celles qui touchent au noyau. Elles sont ensuite rejouées sur les entrées déjà enregistrées pour vérifier qu'elles n'auraient pas aggravé le passé. Si le replay valide, le changement est appliqué, de façon réversible.

🔒
05

Le noyau est intouchable

L'arithmétique des ordres, les règles de risque et les prompts du Risk Manager vivent dans une zone que le système de self-evolution ne peut pas éditer. C'est écrit dans le système de types du code, donc une modification qui vise cette zone ne compile tout simplement pas. Résultat, un agent qui apprend ne peut jamais désactiver son propre frein.

🛡️
06

Résiste au prompt injection

En replay, les auteurs ont injecté dans les news et les filings des instructions malveillantes qui disaient à l'agent de trader autrement. Zéro injection suivie. Le typage force chaque agent à rendre un rapport dans un format strict, donc une instruction en langage libre dans un article n'a aucun endroit où atterrir dans le pipeline de décision.

Ce qu'ils ont mesuré

  • déploiement live 5 mois, 102 jours de trading, 1 632 appels LLM
  • drawdown sectoriel de 24,6 % contenu à une perte de 0,3 %
  • en replay, un seul modèle sur les mêmes données perd 1,35 point contre le marché sur 5 jours là où le système multi-agent ne perd pas significativement ; backtest 2015-2026, le noyau seul baisse le max drawdown sur les 50 politiques d'entrée aléatoires testées

Ce que ça ne prouve pas

  • 5 mois de live, c'est court et probablement un seul régime de marché
  • le replay valide sur les entrées enregistrées, pas sur un marché qui aurait réagi au nouvel agent
  • le papier ne dit pas combien ça coûte en appels LLM par jour, ni sur quels tickers ça tourne

Chez nous

Où ça se branche

aucun branchement direct, la décision de trade vit dans les screeners Python et signal_outcome.db, pas dans un agent LLM

Le plan

  1. ne rien coder côté trading
  2. garder en tête l'idée du scoring nocturne déterministe pour les sorties LLM de la newsletter et du Trade Desk, écrit dans une table signal_llm_grades
  3. si un jour un agent LLM prend une décision irréversible, relire ce papier pour le patron noyau invariant plus replay

Effort

0 h maintenant

Ça remplace

rien, les screeners restent la source de vérité

Le risque

le vrai risque serait de brancher ça pour meubler et d'ajouter une couche d'agents entre mes screeners et mes ordres, ce qui dégraderait un pipeline qui marche

Le test qui tranche

pas de test à lancer, le papier traite un problème que je n'ai pas ; je ne rebranche que si je passe un jour à un agent LLM qui déclenche des ordres, auquel cas le seuil serait un drawdown contenu équivalent au 24,6 % vers 0,3 % mesuré par les auteurs

Ce que j'ai simplifié

  • j'ai dit noyau intouchable comme si c'était magique, en vrai c'est juste que le type system du code interdit certaines éditions
  • j'ai résumé la mémoire en sept couches à quatre éléments, le papier en liste sept dont je n'ai gardé que ceux qui parlent

La falaise de compaction en mémoire d'agents

Quand un agent LLM résume son contexte pour tenir dans la fenêtre, les règles de sécurité se font écraser aussi vite que les logs, et il faut les trier par type pour les garder intactes.

The Compaction Cliff in Long-Running AI Agent Memory · arXiv 2608.22752

PASSER

Le système est un pipeline batch de screeners qui écrivent dans SQLite, les agents LLM y font du mécanique borné et du jugement court, sans long contexte multi-tours à compacter. La falaise de compaction touche les agents conversationnels qui tournent des heures avec des règles de sécurité en fenêtre, cas qui n'existe pas ici.

Le problème qu'ils attaquent

Un agent qui tourne longtemps accumule du contexte jusqu'à saturer sa fenêtre. Au moment de compacter, le résumé traite une règle de sécurité comme une ligne de log. La règle perd sa formulation exacte et devient inapplicable. Les compactions naïves à un seul appel LLM font disparaître la moitié des règles dès le premier tour.

Comment ça marche

📉
01

La falaise après cinq tours

Les auteurs mesurent ce qui reste d'un jeu de règles de sécurité après plusieurs cycles de compaction. Avec le prompt /compact de Claude Code sur Sonnet 4.6, il reste 53 % des règles après un tour et 10 % après cinq. Chaque tour re-résume le résumé du tour précédent. La perte est cumulative et rapide.

🏷️
02

Trier chaque ligne par type

Leur idée est de classer chaque ligne du contexte selon sa nature. Une règle de sécurité, un fait, un log d'action et une observation n'ont pas la même exigence de fidélité. Un classifieur étiquette les lignes une par une. Chaque type reçoit ensuite sa propre politique de compression.

✂️
03

TypeCompact réécrit selon le type

Pour compacter, ils appliquent une règle par type au lieu d'un résumé global. Les règles de sécurité gardent leur formulation exacte, les logs sont agrégés durement. Le compacteur devient déterministe par type. Ils conservent deux à quatre fois plus de règles que le meilleur compacteur LLM à un seul appel.

🧩
04

TypeDecompose partitionne les sujets lourds

Quand un sujet est trop gros pour tenir compact sans perte, ils le coupent en morceaux thématiques. Les règles de sécurité qui s'appliquent au sujet sont recopiées dans chaque morceau. Aucun morceau ne se retrouve orphelin de sa contrainte. Le taux de violation de portée tombe à zéro contre 93 % avec un découpage uniforme.

📥
05

TypeRetrieve épingle les règles

Pour le rappel depuis un stockage externe, ils épinglent d'abord les règles en portée, puis complètent avec les items pertinents. Une règle n'est jamais évincée par un item plus proche sémantiquement. Le rappel à 50 items atteint 100 % contre 73 % pour le meilleur retriever LLM à un seul appel.

🧪
06

Testé sur trois domaines aval

Ils vérifient sur trois benchmarks de comportement d'agent. Sur la conformité médicale, ils battent le compacteur Sonnet de production avec un p inférieur à 10 puissance moins 8. Sur les tâches retail et les tâches airline, ils battent aussi les baselines hiérarchiques. Les gains ne sont pas que des chiffres de compression, ils se voient sur les décisions finales.

Ce qu'ils ont mesuré

  • Compaction Sonnet 4.6 : 53 % de règles préservées après un tour, 10 % après cinq
  • TypeCompact : 96 % de rappel sur les règles après cinq tours, deux à quatre fois mieux que le meilleur compacteur LLM à un seul appel
  • Corpus publié AgentArtifactCorpus : 396 934 configurations d'agents extraites de 54 628 dépôts GitHub publics

Ce que ça ne prouve pas

  • Le classifieur par type est un composant supplémentaire, sa qualité conditionne tout le reste
  • Les benchmarks testés sont conversationnels (médical, retail, airline), pas des pipelines de trading batch qui écrivent en DB
  • Le papier montre la préservation des règles, il ne montre pas de gain P&L ni de gain sur des décisions numériques

Chez nous

Où ça se branche

Aucun point de branchement clair. Les scripts de screener (PULLBACK, BOTTOM, BREAKOUT, VSA, SMART_FLOW, UNUSUAL_V3, STAGE4_MEANREV, VARIANCE_PREMIUM, KERBEROS_RSI, VVIX_SIGNAL) sont sans état LLM long. lib/llm_gateway.py fait des appels courts. Le Trade Desk nocturne tourne une fois par nuit sans compaction.

Le plan

  1. Ne rien coder. Vérifier d'abord qu'un agent maison dépasse vraiment sa fenêtre sur un run réel
  2. Si un futur agent conversationnel apparaît (assistant chat dans l'app payante), relire le papier à ce moment
  3. Retenir la seule idée transférable : étiqueter les prompts système comme non-résumables si un jour on ajoute une couche de mémoire
  4. Sinon, garder le lien du corpus AgentArtifactCorpus pour référence, sans intégration

Effort

0 h

Ça remplace

Rien. Aucun composant actuel ne fait de compaction multi-tours qui perdrait des règles

Le risque

Perdre du temps à intégrer une brique pour un problème qu'on n'a pas. Le signe : impossible de nommer un agent maison qui compacte son contexte plus d'une fois par session

Le test qui tranche

Lister tous les appels LLM du système et compter ceux qui font plus de trois tours dans une même fenêtre avec des règles de sécurité dedans. Si le compte est zéro, le papier ne s'applique pas. Seuil de bascule vers PLUS TARD : au moins un agent qui compacte deux fois ou plus par session en production.

Ce que j'ai simplifié

  • J'ai résumé les trois opérateurs (TypeCompact, TypeDecompose, TypeRetrieve) comme trois politiques par type, le papier détaille plus finement les garanties de fidélité
  • J'ai traité la notion de règle de sécurité comme un texte à préserver mot pour mot, le papier discute aussi de la portée logique de ces règles

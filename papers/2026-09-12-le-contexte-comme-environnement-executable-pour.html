Agents et outillage
Papier de la semaine · samedi 12 septembre

Le contexte comme environnement exécutable pour agents

Les auteurs proposent de gérer la mémoire d'un agent LLM comme un programme Python vivant, où l'agent écrit du code pour retrouver ce dont il a besoin au lieu de tout empiler dans le prompt.

Context as an Environment: Programmatic Context Management for Long-Horizon Agents · arXiv 2608.21690

PASSER

Le système de Daniel tourne sur des scripts Python courts lancés par cron et launchd, avec des sessions LLM brèves qui produisent un livrable et s'arrêtent. Il n'y a pas d'agent long-horizon dont la mémoire déborde du contexte, donc l'appareillage lourd de Scroll ne trouve rien à améliorer ici.

Le problème qu'ils attaquent

Un agent LLM qui tourne longtemps accumule un historique bien plus gros que sa fenêtre de contexte. Les méthodes actuelles compressent ou résument le passé, en devinant à l'avance ce qui servira plus tard. Ce pari est souvent perdu, car on jette une info qui redevient utile dix étapes plus loin. Les auteurs veulent un système où rien n'est perdu et où l'agent va chercher lui-même la bonne info au bon moment.

Comment ça marche

📜
01

Un journal qui garde tout

Chaque action de l'agent, chaque sortie d'outil, chaque message est ajouté à un Event Log. Ce journal ne s'efface jamais et sert de vérité de référence. Si une info a existé un jour dans la session, elle est encore là, adressable par une position exacte. C'est la mémoire longue du système, brute et complète.

🐍
02

Un noyau Python qui persiste

À côté du journal tourne un vrai interpréteur Python en bac à sable. Les sorties d'outils et les résultats sont attachés à des variables typées qui survivent d'un appel du modèle au suivant. L'agent peut donc stocker un DataFrame ou une liste et le rappeler par son nom plus tard. Le prompt n'a plus à recontenir la donnée brute à chaque tour.

⌨️
03

Le modèle écrit du code

Pour retrouver ou transformer une info, le modèle écrit un bout de Python exécuté dans le noyau. Seul ce que le code imprime volontairement revient dans la fenêtre visible du prochain appel. Gérer sa mémoire devient une tâche de programmation, qui profite des progrès des LLM en code. L'agent choisit ce qui remonte à sa vue courante à chaque étape.

📚
04

Éviction avec adresse de retour

Quand la vue de travail sature, les vieux passages sont sortis pour libérer la place. Un petit index d'éviction garde un repère compact pour chaque zone évincée, avec l'adresse exacte dans l'Event Log. Si l'agent a besoin d'un vieux passage, il saute directement à sa position au lieu de fouiller. Rien n'est jamais vraiment perdu, juste rangé plus loin.

🎯
05

Trois bancs de test longs

Ils évaluent le système sur trois épreuves de mémoire longue et d'agent à long horizon. Le modèle qui pilote est Qwen3.8-Max, un LLM open source de grande taille. Les scores montent nettement au-dessus des meilleurs systèmes de mémoire publiés. Le gain le plus gros arrive sur la tâche la plus longue, où les autres approches craquent.

Ce qu'ils ont mesuré

  • 94,8 % de score sur LongMemEval_S avec Qwen3.8-Max
  • 73,1 % sur BEAM_10M, soit 5,1 points au-dessus du meilleur système mémoire publié
  • 86,7 % sur LOCA_256K, soit 37,4 points au-dessus du meilleur agent long-horizon publié

Ce que ça ne prouve pas

  • Résultats montrés avec un seul backbone Qwen3.8-Max, la transposition à Claude ou GPT n'est pas prouvée dans le résumé
  • Un bac à sable Python persistant ajoute une surface d'attaque et un coût d'infra que le résumé ne chiffre pas
  • Le résumé ne donne pas le surcoût en tokens ni la latence par tour par rapport à un simple résumé glissant

Chez nous

Où ça se branche

Rien à brancher. Les scripts screener, lib/llm_gateway.py, le Trade Desk nocturne et les jobs Discord font tous des appels LLM ponctuels sans état inter-appels à préserver.

Le plan

  1. Aucune. Garder l'idée en tête si un jour un agent tourne en boucle sur des heures avec un vrai historique à interroger.

Effort

0 h

Ça remplace

Rien. Le harness actuel n'a pas de composant de gestion de mémoire long-horizon à remplacer.

Le risque

Le vrai risque est de le brancher quand même par curiosité et d'ajouter un noyau Python persistant à maintenir pour zéro gain.

Le test qui tranche

Si un futur agent maison dépasse 50 appels LLM dans une même session avec besoin de relire des sorties d'il y a plus de 20 tours, alors relire ce papier. En dessous, un simple résumé glissant suffit et Scroll est du sur-dimensionnement.

Ce que j'ai simplifié

  • J'ai présenté l'Event Log et le noyau Python comme deux briques séparées, alors qu'ils sont couplés par un système d'adressage précis dont je passe le détail.
  • Les scores cités viennent d'un seul backbone Qwen3.8-Max, je n'ai pas dit à quel point ils dépendent de la qualité du modèle qui écrit le code de gestion mémoire.

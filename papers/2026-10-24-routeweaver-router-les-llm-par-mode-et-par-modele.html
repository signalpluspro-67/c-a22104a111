RouteWeaver : router les LLM par mode et par modèle

Un seul routeur apprend à choisir le mode d'exécution (un coup, plusieurs coups, agent) ET le modèle à appeler pour chaque question.

RouteWeaver: Weaving Mode Selection and Execution into Unified LLM Routing · arXiv 2610.19705

PASSER

Mon routing LLM est déjà résolu par llm_gateway.py avec une table statique PROTECTED, jugement sur Claude et mécanique sur deepseek, et ça coûte peu à maintenir. Entraîner une politique RL pour arbitrer entre single-round, multi-round et agent n'apporte rien à des screeners qui tournent sur des données chiffrées, pas sur des questions NLP ouvertes.

Le problème qu'ils attaquent

Les routeurs LLM actuels fixent d'avance le mode d'exécution. Tu décides une fois pour toutes qu'on fera du single-round, ou du multi-round, ou de l'agentique, et après le routeur choisit juste le modèle dedans. Du coup une question simple paye le coût d'un agent, et une question dure est coincée en un seul coup. Les auteurs veulent un routeur qui bascule entre les modes selon la question.

Comment ça marche

🧭
01

Un routeur, deux décisions couplées

Pour chaque requête, le routeur sort deux choix. Le premier choix dit comment exécuter : un seul appel, un dialogue en plusieurs tours, ou un agent qui boucle avec des outils. Le deuxième choix dit quel modèle appeler dans ce mode. Les deux choix sont faits par la même politique entraînée.

🎯
02

COMET-GRPO sépare le crédit

Quand une trajectoire réussit ou rate, il faut savoir à qui donner la note. Leur algo coupe l'avantage global en deux signaux. Un signal note le choix du mode, l'autre note le choix du modèle à l'intérieur du mode. Chaque décision reçoit son propre feedback, ce qui stabilise l'apprentissage.

📚
03

On apprend les modes avant de choisir

Au début de l'entraînement, le mode est imposé de l'extérieur. Le routeur se contente d'apprendre à bien exécuter dans chaque mode. Petit à petit on lui rend la main sur le choix du mode. Sans cette montée en douceur, le routeur se replie sur le single-round pour toutes les questions.

🧪
04

Testé sur cinq domaines

Ils évaluent sur maths, code, connaissance, raisonnement logique, et rappel factuel. L'idée est de couvrir des questions qui n'ont pas la même forme de solution. Une question de rappel se résout en un coup, un problème de code peut avoir besoin d'un agent avec exécution. Le routeur doit s'adapter domaine par domaine.

💰
05

Gain d'exactitude sur le meilleur baseline

Ils comparent à des routeurs fixés sur un seul mode. Leur système bat le meilleur de ces routeurs sur chacun des cinq domaines, pas juste en moyenne. Le point clé est que le gain vient de pouvoir changer de mode, pas juste de mieux choisir le modèle.

Ce qu'ils ont mesuré

  • Exactitude moyenne 61,4% pour RouteWeaver
  • Gain relatif de 11,03% sur le meilleur baseline
  • Évalué sur cinq domaines : maths, code, connaissance, raisonnement logique, rappel factuel

Ce que ça ne prouve pas

  • Zéro mention d'un critère coût-par-requête, ils optimisent l'exactitude
  • Pas de données financières ni de signal numérique dans l'éval, uniquement du NLP
  • L'ablation montre un effondrement sur single-round sans leur astuce, donc la méthode est fragile
  • Taille d'échantillon et budget d'entraînement pas donnés dans le résumé

Chez nous

Où ça se branche

Rien de pertinent. Les candidats seraient lib/llm_gateway.py et lib/model_tier.py, mais aucun des deux n'a besoin d'un mode agent vs single-round appris, le routage y est déterministe par type de job.

Le plan

  1. Ne pas brancher
  2. Garder llm_gateway.py tel quel
  3. Relire ce papier seulement si un jour le harness LLM gère des questions utilisateur ouvertes qui pourraient demander un agent

Le test qui tranche

Pas de test à lancer, le papier ne s'applique pas. Si un jour tu veux retester : mesurer sur un mois le pourcentage d'appels dans llm_gateway qui bénéficieraient d'un mode multi-tour, et laisser tomber en dessous de 20%.

Spécialiser un LLM pour écrire du Backtrader

Les auteurs entraînent un modèle de langage à écrire du code de stratégie de trading dans un framework précis (Backtrader), et montrent que deux étapes d'entraînement sur du code de ce framework font passer la réussite de 27% à 58%.

QuantCode Model: Specializing Language Models for Executable Algorithmic Trading Code · arXiv 2609.39420

PASSER

Le système ici ne génère pas de code de stratégie à la volée, les 10 screeners sont écrits et validés à la main en 8 étapes maison. Spécialiser un LLM pour écrire du Backtrader n'a aucun client dans ce stack, et en plus ça casserait le tool calling dont dépend le harness d'agents.

Le problème qu'ils attaquent

Un LLM générique sait écrire du Python moyen, mais quand on lui demande une stratégie exécutable dans un framework de backtest précis, il se trompe sur les classes, les signatures et la logique d'ordre. Le code tourne mal ou pas du tout. Les gens finissent par corriger à la main. Les auteurs cherchent une recette pour que le modèle sorte du code juste du premier coup, et qu'il sache aussi réparer son propre code quand le backtest casse.

Comment ça marche

📚
01

Lire tout le code Backtrader

Première étape, ils font du pré-entraînement continu. Le modèle avale le code source du framework Backtrader et des stratégies publiques écrites avec. Il apprend les noms de classes, les hooks, les patterns typiques. À la sortie il parle couramment Backtrader avant même qu'on lui demande une stratégie.

🎓
02

Imiter des exemples validés

Deuxième étape, le fine-tuning supervisé. Ils construisent des paires demande en langage naturel → code qui tourne, filtrées par un agent qui exécute le backtest pour vérifier que ça marche. Le modèle apprend à mapper une consigne vers un code qui passe. C'est la couche qui transforme un modèle qui connaît le framework en modèle qui obéit.

🧪
03

Un benchmark de 400 tâches

Ils mesurent sur QuantCode-Bench, 400 descriptions de stratégies à coder. Un juge note si le code sort juste du premier coup (Judge Pass) et si le backtest s'exécute sans erreur. Ils ajoutent une piste style SWE-bench où le modèle doit modifier un dépôt existant, pas juste écrire un fichier.

🔁
04

Un agent qui répare

Dans l'évaluation agentique, le modèle a jusqu'à dix tours pour réparer son code quand le backtest échoue. Il lit l'erreur, retente, recommence. C'est le scénario réaliste d'un harness qui boucle. La version fine-tunée réussit 79% des cas à la fin, contre 47% pour le modèle de base.

⚠️
05

La spécialisation casse autre chose

Effet secondaire gênant. Quand on spécialise lourdement sur Backtrader, le modèle oublie comment formater des appels d'outils structurés que le parser attend. Il devient moins bon agent général. Ils rattrapent le formatage avec un petit SFT ciblé, mais la performance sur du code de dépôt reste dégradée.

📏
06

Pré-entraînement seul ne suffit pas

Le pré-entraînement sur le code Backtrader améliore le premier jet, mais fait baisser la réussite finale après réparations. Le modèle devient moins obéissant quand on lui demande de corriger. Le SFT après pré-entraînement est ce qui améliore les deux à la fois. L'ordre et la combinaison comptent.

Ce qu'ils ont mesuré

  • Judge Pass passe de 27.8% à 58.2% sur Qwen3.6-35B après pré-entraînement puis SFT, avec 83.5% de backtests qui s'exécutent
  • en mode agent avec 10 tours de réparation, la réussite finale passe de 47.5% à 79.5% après SFT
  • benchmark de 400 tâches de génération de stratégies Backtrader, plus une piste au niveau dépôt

Ce que ça ne prouve pas

  • le papier teste Backtrader, aucun chiffre sur un framework maison en Python pur
  • la spécialisation détruit le tool calling, ce qui gêne pour brancher le modèle dans un harness qui parse du JSON
  • le juge est un LLM, Judge Pass ne garantit pas que la stratégie générée soit rentable en live
  • aucune mesure de qualité financière des stratégies produites, juste de leur exécutabilité

Chez nous

Où ça se branche

aucun fichier concerné. Le harness LLM appelle des modèles pour poster dans Discord et écrire des HTML, il n'écrit pas de code de screener. Les screeners vivent dans scripts-screener en Python, pas en Backtrader.

Le plan

  1. ne rien coder
  2. garder en tête que spécialiser un modèle casse ses capacités d'agent, si un jour on fine-tune un modèle maison
  3. si on veut un jour générer des idées de stratégies en langage naturel, repartir d'un modèle généraliste et valider à la main

Effort

0 h

Ça remplace

rien

Le risque

le vrai risque est de se laisser tenter par la mode fine-tuning et perdre une semaine pour un gain nul sur un stack qui n'écrit pas de code de stratégie

Le test qui tranche

pas de test à lancer. Le papier serait pertinent si un jour le système devait générer du code de stratégie à partir d'une consigne texte, et dans ce cas le seuil d'intérêt serait un Judge Pass au-dessus de 60% sur des stratégies traduites dans le framework maison, pas Backtrader.

Ce que j'ai simplifié

  • j'ai dit Backtrader comme si c'était un seul framework, en vrai la piste SWE-bench teste aussi la modification de dépôts plus larges
  • j'ai résumé le SFT comme de l'imitation, en pratique il y a un agent qui valide chaque exemple en l'exécutant avant de l'ajouter au jeu d'entraînement

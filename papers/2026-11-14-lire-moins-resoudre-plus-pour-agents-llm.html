Agents et outillage
Papier de la semaine · samedi 14 novembre

Lire moins, résoudre plus pour agents LLM

Une couche logicielle qui empêche un agent LLM d'avaler des pages entières quand il lui faut trois lignes, pour payer moins de tokens et aller plus vite.

Read Less, Solve More: Token-Efficient Sparse Reading of External Content for AI Agents · arXiv 2608.22237

PASSER

Le système ici est un screener quantitatif sur base EOD Polygon, pas un agent qui lit des pages web pour répondre. Les seuls bouts qui touchent du LLM sont le harness Discord et les pages HTML, et ils consomment peu de contenu externe par appel.

Le problème qu'ils attaquent

Les agents qui naviguent sur le web ou lisent des documents ingurgitent souvent tout le contenu alors qu'une petite partie suffit à répondre. Ça coûte cher en tokens, ça ralentit, et le vrai signal se noie dans le bruit. Les solutions existantes modifient le modèle ou forcent un format rigide. Les auteurs veulent une brique réutilisable qui se glisse entre l'agent et ses sources sans toucher au modèle.

Comment ça marche

📜
01

Suivre l'intention de lecture

Un protocole garde en mémoire ce que l'agent cherche vraiment à chaque étape. Il note aussi quelles sources ont déjà été survolées et jusqu'où. Quand l'agent demande à lire quelque chose, la couche compare la demande à ce besoin. Elle peut refuser, filtrer ou rogner avant de servir le contenu.

🔌
02

Backends de lecture interchangeables

Chaque type de source a son module de lecture dédié. Une page HTML, un dépôt de code et une réponse d'API ne se fouillent pas pareil. Le module décide comment localiser la preuve utile, par exemple par recherche ciblée ou par extraction de section. L'agent appelle toujours la même interface, la couche choisit le bon outil derrière.

🚦
03

Porte de lecture budgétée

La couche fixe un plafond total de contenu brut qu'un épisode peut consommer. Chaque lecture décompte des tokens de ce budget. Si la demande dépasse, la porte résume ou tronque. En cas de doute, elle sait basculer en lecture complète pour ne pas rater une preuve critique.

🧰
04

Interface unifiée côté agent

L'agent voit un seul objet Reader quelle que soit la source. Il demande de la preuve, pas un fichier entier. Ça rend le code de l'agent plus simple et plus stable quand on change de type de source. Les mêmes prompts marchent sur une page web, un PDF ou une sortie d'outil.

🧪
05

Évaluation sur six modèles

Les auteurs testent la couche avec six modèles différents, dont Claude Opus 5, sur cinq scénarios. Ils mesurent les tokens consommés, le temps réel écoulé et la qualité de la tâche. Ils comparent à l'agent sans la couche, sur les mêmes requêtes. Ils refont le test en l'intégrant à trois frameworks d'agents pour montrer que c'est portable.

🧩
06

Ablations des trois pièces

Ils retirent une à une les trois briques pour voir laquelle fait quoi. Sans le suivi d'intention, la qualité chute. Sans les backends dédiés, le temps explose. Sans le budget, les tokens repartent vers le haut. Les trois servent, aucune n'est décorative.

Ce qu'ils ont mesuré

  • jusqu'à 92,9 % de tokens économisés et 89,0 % de temps réel en moins sur les cinq scénarios
  • sur les tâches de recherche web profonde, 31,0 à 43,0 % de tokens en moins et 23,0 à 37,0 % de temps de complétion en moins
  • six modèles testés dont Claude Opus 5, cinq scénarios, intégration validée dans trois frameworks d'agents, qualité préservée ou améliorée dans 97 % des cas

Ce que ça ne prouve pas

  • le résumé ne donne pas la qualité chiffrée par scénario, juste un taux global de 97 %
  • la couche est pensée pour des agents qui lisent du contenu externe, le gain pour un pipeline de données tabulaires n'est pas démontré
  • on ne sait pas comment le budget se règle en pratique, ni ce qui se passe quand le fallback plein se déclenche souvent

Chez nous

Où ça se branche

Le seul endroit vaguement concerné serait le harness d'agents LLM qui poste dans Discord et génère les pages HTML, pas les screeners PULLBACK, BOTTOM, BREAKOUT, VSA, SMART_FLOW, UNUSUAL_V3, STAGE4_MEANREV, VARIANCE_PREMIUM, KERBEROS_RSI, VVIX_SIGNAL, ni les bases signal_outcome.db et market_data.db.

Le plan

  1. Ne pas brancher.
  2. Garder la référence au cas où un futur agent LLM maison irait lire des 10-K, des dépôts 13F ou des pages de news en volume.
  3. Si ce cas arrive, commencer par mesurer les tokens actuels par appel LLM pour voir s'il y a vraiment un problème à résoudre.
  4. Seulement alors regarder si le Read Intent Protocol et la porte budgétée valent l'intégration.

Effort

0 h aujourd'hui, à reconsidérer si un agent de lecture profonde est ajouté

Ça remplace

Rien. Le harness actuel appelle des modèles sur des prompts courts, il ne consomme pas de longues pages externes.

Le risque

Le signe qu'il faudrait revenir à ce papier, c'est une facture LLM qui grimpe parce qu'un agent se met à aspirer des documents entiers pour le tracker Congrès ou les 13F.

Le test qui tranche

Mesurer la part des tokens LLM mensuels qui sert à ingurgiter du contenu externe brut. Si c'est sous 20 % de la facture, le papier ne rapporte rien ici, on le classe. Au-dessus, on relit.

Ce que j'ai simplifié

  • J'ai décrit la porte budgétée comme un simple plafond, le papier parle d'exposition cumulée avec fallback, c'est un peu plus fin.
  • Les backends adaptatifs recouvrent sans doute plusieurs stratégies de recherche interne que je résume en un seul mécanisme.

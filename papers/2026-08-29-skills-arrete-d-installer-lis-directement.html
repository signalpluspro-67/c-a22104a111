Papier de la semaine · samedi 29 août

@skills : arrête d'installer, lis directement

Un protocole ouvert pour utiliser des compétences d'agents LLM en les lisant à la demande via un chemin, au lieu de les installer et de saturer le prompt système.

@skills: Attention is all you have · arXiv 2608.12610

PASSER

Ton système n'utilise pas d'agents multi-skills avec un prompt saturé, tu as un harness Python maison qui route les jobs par nom de fichier et non par description de skill. Le problème que ce papier résout n'existe pas chez toi.

Le problème qu'ils attaquent

Aujourd'hui il existe 56 804 skills publics pour agents LLM, plus tout ce que les équipes écrivent en interne. Le modèle standard consiste à installer un skill, ce qui garde sa description en permanence dans le prompt système. Or un prompt a moins de 100 emplacements fiables où un skill peut se déclencher automatiquement, donc les skills se battent pour la place. La longue traîne devient inutilisable et les playbooks maison de l'équipe se retrouvent en concurrence avec des skills qu'ils n'utilisent presque jamais.

Comment ça marche

📦
01

Installer fait trois choses

Quand tu installes un skill, tu obtiens en réalité trois choses collées ensemble. Le contenu du skill lui-même, sa présence permanente dans le prompt, et le déclenchement automatique quand l'agent voit une tâche qui matche. Le papier remarque qu'une seule de ces trois choses a vraiment besoin d'occuper de la place dans le prompt, la dernière. Les auteurs proposent de séparer les trois.

🔗
02

Le chemin remplace l'installation

Un skill est identifié par un chemin, par exemple gh:user/repo ou un chemin local. L'agent peut lire ce chemin quand une tâche le demande, exécuter le skill, et passer à autre chose. Rien ne reste résident dans le prompt entre deux usages. Lire le skill suffit à s'en servir.

📂
03

Vendoring dans ton dépôt Git

Quand tu veux vraiment adopter un skill, l'opération copie ses fichiers à ce chemin dans l'arbre Git de ton projet. Tu deviens propriétaire de cette copie et tu peux la modifier comme n'importe quel fichier. Le format SKILL.md du skill ne change pas, donc les skills existants marchent tels quels. Un dossier devient un menu, donc un bundle est juste un dossier ordinaire dans lequel l'agent pioche.

🎯
04

Une seule ligne coûte du prompt

Le seul élément qui reste résident dans le prompt système est une ligne de style .gitignore, qui déclare quels chemins l'agent doit surveiller pour un déclenchement automatique. Tout le reste vit sur disque et se lit à la demande. Tu choisis explicitement les rares skills qui méritent d'occuper un slot de déclenchement. Les autres restent accessibles par chemin sans coûter un octet de prompt.

🔍
05

Un hub pour chercher

Un chemin sait pointer vers un skill, mais il ne sait pas le trouver. Les auteurs ont donc monté un hub gratuit à atskills.one qui indexe les skills et permet de chercher dedans, avec hébergement sans dépôt et collections privées. Le hub reste optionnel, les chemins gh: et locaux marchent sans lui. Un skill indexé garde son identité gh: d'origine.

🛠️
06

Aucune infra à ajouter

Le protocole ne demande ni manifest, ni lockfile, ni registration. N'importe quel agent qui sait lire un fichier et lancer une commande devient client via un unique fichier d'instructions. Le protocole est additif, donc il cohabite avec ce qui existe déjà. Une implémentation de référence tourne dans la CLI AdaL.

Ce qu'ils ont mesuré

  • 56 804 skills publics d'agents recensés au moment du papier
  • Moins de 100 slots de déclenchement fiables dans un prompt système, d'après leur mesure
  • Le papier ne donne pas de benchmark de performance ni de taille d'échantillon utilisateurs

Ce que ça ne prouve pas

  • Le papier ne mesure pas si un agent choisit mieux ses skills quand il doit les lire par chemin plutôt que les voir en permanence
  • Ça casse si l'agent ne pense jamais à aller lire le chemin, puisque plus rien ne le rappelle dans le prompt
  • La question de la découverte reste ouverte, le hub externe est un pansement qui recrée une dépendance

Chez nous

Où ça se branche

Rien à toucher. Ni lib/llm_gateway.py, ni lib/model_tier.py, ni les screeners, ni les bases signal_outcome.db et market_data.db. Le harness Python appelle des modèles par jobs nommés, pas par sélection dynamique de skills dans un prompt système.

Le plan

  1. Ne rien coder côté production
  2. Éventuellement, si un jour tu construis un agent Claude Code qui a plus de 30 skills, revenir lire ce papier
  3. En attendant, garder le lien du hub atskills.one comme signet de veille
  4. Continuer à écrire tes skills Claude Code directement dans ~/.claude/skills sans indirection

Effort

0 h

Ça remplace

Rien. Ça ne remplace rien dans ton pipeline de trading, ça vise un problème d'agents généralistes.

Le risque

Le risque serait justement de le brancher pour rien et d'ajouter une couche d'abstraction sur un système qui marche déjà en direct. Signe que tu te trompes : tu passerais du temps à faire cohabiter un protocole avec ton harness sans gain mesurable sur la qualité des signaux.

Le test qui tranche

Compte le nombre de skills dans ton dossier ~/.claude/skills que Claude Code voit d'un coup. Tant que c'est sous 50 et que tu n'observes pas de skill fantôme qui se déclenche à tort, aucune raison de bouger. Si un jour tu passes 100 skills et que tu vois Claude en oublier ou en mélanger, alors relis le papier.

Ce que j'ai simplifié

  • J'ai raccourci le mécanisme du hub, il gère aussi le ranking et l'authoring en une page
  • J'ai simplifié la partie vendoring, en pratique elle règle aussi la question de la version figée et de la propriété du code
